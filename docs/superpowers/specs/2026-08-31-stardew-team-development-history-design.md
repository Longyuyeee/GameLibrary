# 星露谷物语团队与开发历程专题重建设计

## 目标

将《团队与开发历程》从混合估算、错误版本说明和无来源行业评论，重建为截至 2026-08-31 可复核的开发档案。完成标准不是篇幅，而是资料族范围明确、来源固定、预期与实际差异为 0、时间敏感事实注明观察日期。

## 方案比较

1. 保留原文并逐句补引用：改动小，但错误事实、平台估算和主观分析互相缠绕，难以证明完整。
2. 按年月写长篇叙事：阅读自然，但团队、版本、平台和发行权容易重复，无法稳定计数。
3. 按资料族重建总账：分别维护团队/合作方、PC 大版本、平台首发、发行权、销量和技术事实，并将游戏内容跳转现有专题。

采用方案 3。它最适合当前图书馆的“先定义全集再对账”和唯一归属规则。

## 信息边界

- 本页维护开发者、合作公司、版本与平台发布时间、发行权、官方销量快照和开发工具。
- 版本具体新增物品与机制不在本页复制，跳转现有机制、数值和特色专题。
- 不保留平台销量推算、实时商店评价、主观世界排名、未注明奖项口径、无法定位原文的“启示”或引语。
- “当前”销量和后续更新状态都标明截至 2026-08-31，避免把时间敏感数据写成永久事实。

## 导航与关联更新

保留顶部面包屑和页尾连续导航；同步游戏概览大小、剧情入口、星露谷审计记录、全库计划和既有审计契约。下一阶段改为加工制造剩余比较来源。

## 真实测试

1. 红灯：来源断言应通过；旧文档对新范围应出现缺失和陈旧事实。
2. 绿灯：用同一组必需/陈旧断言验证差异归零。
3. 数量审计：团队阶段、PC 版本、平台组、自发行阶段、销量快照、技术事实与固定来源逐族计数。
4. 回归：运行全部 `审计星露谷*.py`，再运行 `git diff --check`、链接审计和 Git 边界审计。
